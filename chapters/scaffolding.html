Scaffolding

“Best practices” for using AI in coding is a rapidly expanding, and rapidly contradicting, body of advice. Everyone seems to be saying something slightly different, and much of it is still being figured out in real time. Rather than trying to survey all of it, this session focuses on one particular idea: scaffolding. This approach follows an interview of Carlos Kelkboom, a leading Software Architect, whose framing of the problem I personally find especially compelling and practical.

What is Scaffolding?

Scaffolding means building the “skeleton” of your project out of plain words and empty files before you let the AI write a single line of actual R code. Think of it this way: the AI is a remarkably fast builder, but you are the Chief Architect. If you do not draw up the blueprint first, the AI will cheerfully build the wrong house, quickly, confidently, and with code that runs without error.

Scaffolding means deciding upfront which part of the code is responsible for what, and exactly what data gets passed between those parts, while those decisions are still easy to change, before a lot of implementation gets built on top of them. Once an agent has already written five hundred lines of interdependent code, restructuring becomes expensive and risky. Deciding before that point what talks to what, what a function is responsible for, and what it should never touch, costs you a few minutes of thinking instead of hours of untangling.

Step-by-Step Guide to Scaffolding

1. Discuss project structure with AI

Before any code is written, talk through the shape of the project with the AI, treating it as a sounding board rather than a builder.

  • Ask for critiques of existing projects or structures, especially if you are working in a domain that is unfamiliar to you. Show the AI a folder layout or an existing script and ask it to point out weaknesses, rather than asking it to design from scratch.
  • Do not let the AI implement anything at this stage. It will keep pushing to write code for you, because that is what it is optimized to do. Resist that. Your job here is to think, not to produce.

2. Set up the folder structure

Translate the discussion above into an actual, if mostly empty, folder and file layout. This is still just words and placeholders, no real logic yet.

3. Add comments

Inside each empty or near-empty file, write comments describing what that file is supposed to do, before any function body exists.

4. Define function names and interfaces (inputs, outputs)

Decide, and write down, the names of your key functions and what goes in and comes out of each one. You are not implementing the logic yet, only pinning down the contract each function must honor.

Micro One-Shot

Carlos’s own practice, once the architecture is settled, is to hand a large task to the agent in a single pass and let it produce a complete solution in one shot. For many of us, though, reviewing a one-shot of an entire project in one sitting can be daunting. The diff is enormous, your attention inevitably drifts, and subtle problems slip through simply because there is too much to hold in your head at once. Also, for a local AI model, large one-shot generations tend to perform poorly compared to their cloud counterparts, since local models are typically smaller and less capable of holding an entire project’s context in mind at once.

So here, we adapt Carlos’s philosophy to micro one-shots, keeping the underlying principle, clear boundaries before execution, while shrinking the scale at which we apply it:

  • Still write a good scaffold first. This part does not change.
  • One-shot small, digestible sections, one function, one file, one well-defined chunk at a time, rather than the whole project at once.
  • Review the output, run it, and if it does not work or you cannot fully understand it, throw it away and revise your instructions rather than patching broken code you do not understand.

This keeps the review burden manageable, works even on local models with limited context, and still gives you the core benefit of scaffolding: you always know what each piece is supposed to do before the AI writes it.

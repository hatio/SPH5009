Version Control via Git

Now that you have a reproducible code and environment to share with your colleagues, or your future self, the next question is: how do you actually share it?

Sharing Code: The Wrong Way(s) and the Right Way

Think about how you might share an R script with a classmate or colleague. Chances are it looks something like one of these:

  • Emailing scripts back and forth. It’s hard to track which version of code was used to generate what results, and nobody can say for certain which copy is the current one. Email attachments also strip away your folder structure, which you now know is essential for reproducibility.

  • Putting files in a synced drive (Dropbox, Google Drive, OneDrive, etc.). It’s hard to track when things get changed, by whom, and for what reason. There’s no clear trace of changes, which makes it challenging to revert cleanly when something breaks.

Advantages of Version Control

  • Complete history: Every change is recorded, along with who made it, when, and (ideally) why.
  • Safe experimentation: You can try out new approaches on “branches” without risking your working code.
  • Collaboration: Multiple people can work on the same project simultaneously, and Git provides tools to merge everyone’s changes together sensibly.
  • Accountability and reproducibility: Combined with what you learned about renv last section, Git lets you say precisely “this exact version of the code, with this exact environment, produced this exact result.”

What is Git?

Git is a distributed version control system (DVCS). In plain terms: it’s a tool that takes periodic “snapshots” of your project folder (called commits), and keeps a complete history of those snapshots so you can inspect, compare, or revert to any of them at any time.

The word distributed matters. In older, centralized version control systems, there was one central server holding the “real” history, and everyone’s computer held just the files they were currently working on. If the central server went down, nobody could see the project history. With Git, every single person who clones a project gets the entire history, on their own machine. There is no single point of failure, and you can commit, branch, and review history even while offline. (see Conceptual diagram.)

In everyday use, Git tracks your files through a simple pipeline: changes you make live in your working directory, you selectively mark the changes you want to record using git add (moving them to the staging area), and then git commit permanently saves that snapshot into your local repository. Whenever you’re ready to share your work, git push sends your commits to a remote repository that others can access, and git pull (or git fetch) brings down commits that others have made.

What is GitHub? Is It the Only Option?

Git itself is just a program that runs on your computer. It does not require the Internet, and it does not require GitHub. GitHub is a separate, web-based hosting service for Git repositories. It stores a copy of your repository “in the cloud” so that you and your collaborators have a shared, always-available remote to push to and pull from, plus a web interface for browsing code, discussing changes, and managing projects.

GitHub is simply the most popular option, but it isn’t the only one. Alternatives you’ll encounter include GitLab and Bitbucket, which offer similar hosting with their own features, and many organizations (hospitals, universities, government agencies working with sensitive health data) run their own self-hosted Git servers. You can even push and pull between two personal computers directly, with no hosting service involved at all, since Git fundamentally only needs a reachable file location to treat as a “remote.” For this course, we’ll use GitHub because of its popularity, its free tier for public and private repositories, and its gentle integration with RStudio.

Setting up GitHub

Step 1: Sign Up for a GitHub Account

If you don’t already have one, create a free account at github.com. Use an email address you’ll have long-term access to (not one tied to an employer or school you might leave), since this account will likely follow your work for years.

Step 2: Install Git and Connect It to RStudio

  1. Install Git on your computer, if it isn’t already installed:

    • Windows: Download and install from git-scm.com.
    • Mac: Install via Xcode Command Line Tools (run xcode-select --install in Terminal) or download from git-scm.com.

  2. Open RStudio and go to Tools → Global Options → Git/SVN. Confirm that RStudio has correctly detected the path to your Git executable.

  3. Tell Git who you are (run once, in the RStudio Terminal tab, not the R console):

    git config --global user.name "Your Name"
git config --global user.email "your_email@example.com"

    Use the same email address as your GitHub account so your commits are correctly linked to your profile.

  4. Set up authentication between RStudio and GitHub. GitHub no longer accepts your account password for this; instead, you’ll generate a Personal Access Token (PAT). The usethis R package makes this painless:

    install.packages("usethis")
usethis::create_github_token()   # opens GitHub in your browser to generate a token
gitcreds::gitcreds_set()         # paste the token here to store it securely

For a more detailed, well-regarded walkthrough of this entire setup process, Jenny Bryan’s online guide Happy Git and GitHub for the useR is an excellent free resource, and is used in many university-level R courses. The RStudio documentation on version control with Git is also a concise companion reference.

Step 3: Create Your First Repository

  1. Open the RStudio Project you want to turn into a Git repository (for example, your week3-renv-practice project, or a fresh project with your analysis.R script from Exercise 3.1). In the R console, run:

    usethis::use_git()

    You’ll be asked whether to commit all existing files as a first commit, type 1 for Yes. RStudio will then restart the project. Once it reopens, you should see a new Git pane (top right, next to Environment/History), confirming your project is now a Git repository.

  2. Push this repository to GitHub, creating the remote copy, directly from R:

    usethis::use_github()

    This creates a new repository under your GitHub account with the same name as your project, links it to your local repo, and pushes your commit(s) up in one step. When it finishes, your repository’s URL will print in the console; open it in your browser to confirm your files are there. By default this creates a public repository, which is what you want for this exercise so your friend can access it.

    If use_github() doesn’t work for you (for example, if authentication isn’t configured correctly), you can instead create the repository manually: go to github.com, click the + icon (top right) → New repository, give it a name, keep it Public, and click Create repository (leave “Add a README” unticked, since your project already has files). GitHub will show you a page with commands under “…or push an existing repository from the command line”; copy the two git remote add origin ... and git push ... lines and run them in RStudio’s Terminal tab.

  3. Add or edit a file (for example, edit the README.md, or confirm your analysis.R script is present). Then, in RStudio’s Git pane, tick the checkbox next to the changed file(s) to stage them, click Commit, write a short commit message describing what changed, and click Commit again.

  4. Click Push (the green up-arrow icon) to send your commit up to GitHub.

  5. Send the repository link to a friend. They can clone it themselves (File → New Project → Version Control → Git in their own RStudio, pasting in your repository’s URL from the green Code button on GitHub) or, if you add them as a collaborator (Settings → Collaborators on GitHub), they can push changes back too.

  6. When your friend makes changes and pushes them, click Pull (the blue down-arrow icon) in your own RStudio Git pane to bring their changes down into your local copy.

A note on the commit hash: After committing, look at the History view in the Git pane (the clock icon). Each commit is labeled with a hash. You can always reference a specific commit by this hash, which is how you’d tell someone exactly which version of your project to check out or restore.

Every commit you make is given a unique identifier called a hash (something like a3f5c9e..., a long string of letters and numbers). This hash isn’t arbitrary. It’s generated from the content of the commit itself, so even the tiniest change to your code produces a completely different hash. This is actually a core part of what makes Git trustworthy for reproducibility: you can tell someone “run commit a3f5c9e” and know, with certainty, they are running the exact same code you ran, not some similar-looking copy.

Step 4: Comments and Issues on GitHub

GitHub isn’t just for code storage. It includes lightweight project management tools built around your repository:

  • Comments on commits: Click any commit in your repository’s Commits tab on GitHub, and you can leave a comment directly on it, useful for asking “why did you change this line?” or leaving feedback.
  • Creating an Issue: On your repository’s GitHub page, click the Issues tab → New issue. Issues are used to track bugs, questions, or tasks, for example, “Script fails when df has missing values.” Give it a clear title and description.
  • Resolving an Issue: Once the problem is fixed (perhaps in a later commit), you can reference the issue number in your commit message (e.g., Fixes #3), which will automatically close it on GitHub once pushed. Alternatively, open the issue directly and click Close issue once resolved, optionally leaving a comment explaining the fix.

You now have the final piece of a reproducible, shareable workflow: your data, your code, your environment (via renv), and now your version history (via Git and GitHub), all able to travel together as a single, inspectable package.

Exercise 3.2:

  1. Pair with a friend in class. Pull each other’s repository.
  2. Your friend should open your project, run renv::restore(), and then try running your R script.
  3. Is it reproducible? Did they get the exact same outputs? Discuss any differences and improve your script and renv setup as per your peer’s feedback.
